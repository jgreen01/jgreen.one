# Everything here is allowed, deliberately. The groups below say so by name,
# and the reasoning is at the bottom.
#
# Each group also states what may be done with what it fetches, using the
# Content-Usage rule from the IETF AIPREF drafts (draft-ietf-aipref-attach for
# the syntax, draft-ietf-aipref-vocab for the vocabulary). All three categories
# are stated because an omitted one means "unknown" rather than "yes":
#
#   train-ai  modifying the learned parameters of a generative model
#   ai-use    using this page as model input the user did not supply
#   search    indexing it to point people back here
#
# A blank line ends a group, so the directive sits directly under the Allow it
# belongs to rather than being written once at the top.
#
# The same permissions are stated twice, in two vocabularies:
#
#   Content-Usage   the IETF AIPREF rule, standards track, not yet read by
#                   anything in the wild
#   Content-Signal  Cloudflare's spelling, which their network and the
#                   readiness scanners do read today
#
# They map one to one — train-ai/ai-train, ai-use/ai-input, search/search — and
# both treat an omitted category as neither granted nor refused. Separate
# directive names, and RFC 9309 requires a parser to ignore records it does not
# recognise, so the two coexist without interfering.
#
# Stating a thing twice is only safe while both copies agree, so a build test
# asserts they do, per group. If one vocabulary changes and the other does not,
# that test fails rather than the file quietly saying two different things.

User-agent: *
Allow: /
Content-Usage: train-ai=y, ai-use=y, search=y
Content-Signal: search=yes, ai-input=yes, ai-train=yes
