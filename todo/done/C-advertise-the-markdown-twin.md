# Advertise the Markdown twin to agents

**Priority**: MEDIUM
**Status**: DONE
**Created**: 2026-09-15
**Updated**: 2026-09-16

## Description

Every entry has a Markdown twin and content negotiation works, but nothing on
the page says so. An agent finds it only by already knowing the convention, by
reading `/llms.txt`, or by sending `Accept: text/markdown` speculatively.

Verified live 2026-09-15:

| URL | `Accept: text/markdown` returns |
|---|---|
| `/entries/this-site/` | `text/markdown; charset=utf-8` |
| `/` | `text/html` |
| `/blog/` | `text/html` |

The feature works exactly where twins exist. An isitagentready.com scan tested
the homepage, got HTML, and concluded "site does not support Markdown for
Agents" — a fair result for the URL it tried, and a misleading description of
the site.

**The llms.txt specification recommends exactly this work.** It names three
complementary ways to advertise a Markdown version, and the site does only the
first:

1. **URL convention** — append or replace the extension. Done:
   `/entries/<slug>/index.md`.
2. **HTML link element** — `rel="alternate" type="text/markdown"`. Missing.
3. **HTTP Link header** — the same relation, which "works for all resource
   types". Missing.

`alternate` is a registered IANA link relation and means an alternate
representation of the current resource, which is precisely what the twin is.
This is not a novel convention being invented for the site.

## What the negotiation contract should look like

Cloudflare's "Markdown for Agents" is the de facto description of this
behaviour and what the scanner tests against:

- request carries `Accept: text/markdown`
- response is `text/markdown; charset=utf-8` — **the site already matches this
  exactly**, including the charset, on `/entries/*`
- optionally `x-markdown-tokens`, an estimated token count, so a client can
  budget context before fetching

The token header is a genuinely nice fit here: the site's own article claims
roughly 73% fewer tokens for the Markdown twin, and this would let an agent
confirm that from a HEAD request rather than take the claim on faith. It needs
a CloudFront response headers policy — see the constraint below.

## Full coverage: a twin for every page

The question is whether negotiation should work everywhere rather than only on
entries. It can, and the argument for doing it fully rather than partially is
safety, not completeness — see the edge-function constraint at the end.

Twins are generated by explicit `.md.ts` API routes, not by conversion:
`src/pages/entries/[slug]/index.md.ts` builds one from collection data via
`entryMarkdown()`, and `llms.txt.ts` already generates a whole document from
the collection. That is the pattern to extend.

The eleven routes fall into three groups.

### 1. Listings — straightforward

`/`, `/blog/`, `/projects/`, `/entries/`, `/tags/`, `/tags/<tag>`

Content is derived from the `entries` collection, so a `.md.ts` route can
generate the twin the same way `llms.txt.ts` does. Nothing is authored twice
and nothing can drift, because the collection is the single source. The
per-tag route needs `getStaticPaths` mirroring `tags/[tag].astro`.

### 2. Prose pages — the actual work

`/about` and `/contact`

Their prose lives as HTML inside `.astro` files with no Markdown source:
`about.astro` is four paragraphs, about 1.1 KB. Three ways to handle it:

- **Move the prose into a content collection** (a small `pages` collection),
  render the HTML from it and generate the twin from the same source. Single
  source, no drift, and it matches how entries already work. Preferred.
- **Hand-write the twins.** Two files that must be kept in step with two other
  files by memory. They will drift.
- **Convert HTML to Markdown at build.** Adds a dependency, is lossy, and would
  have to be taught to ignore the nav, header and footer chrome.

`/contact` is nearly free either way: it already renders from
`src/utils/contact.ts`, so its twin can be generated from the same object, as
`contactBlock()` does elsewhere.

### 3. `/404` — skip

An error page has no reader to serve a twin to.

## The constraint that decides the design

The edge function currently rewrites only when the path starts with `/entries/`
and has exactly one segment. Full coverage means mapping any HTML path to
`<path>index.md`.

**The rewrite must never point at a twin that does not exist.** If it rewrites
`/foo/` to `/foo/index.md` and nothing is there, the origin 404s — and since
403 and 404 are now remapped to the 404 page, a URL with perfectly good HTML
would answer 404 to any agent sending `Accept: text/markdown`. That is a worse
failure than having no twin at all, and it would be invisible to anyone
browsing normally.

So there are two consistent designs, and a dangerous middle:

- **Blanket rule, every page has a twin.** The function rewrites unconditionally
  and the invariant is simple enough to test: every HTML route in `dist/` has a
  sibling `.md`.
- **Explicit list.** The function rewrites only known prefixes. Safe, but the
  list has to be kept in step with the routes, by hand, in ES5.1, in the one
  file where a mistake takes the whole site down.

The middle — a blanket rule with a few pages missing twins — is the one to
avoid. This is the strongest argument for doing all pages rather than some.

`infra/live/function.js` runs on every request and an unhandled exception there
returns 503 for all of them. It is ES5.1 syntax only, covered by
`tests/unit/cloudfrontFunction.test.ts` and gated on deploy by
`scripts/test-cloudfront-function.sh`, which runs it in CloudFront's real
engine. Any change here goes through both.

## Acceptance Criteria

- [x] Entry pages carry `<link rel="alternate" type="text/markdown" href="…">`
      pointing at the twin, absolute, built from the same helper that produces
      the canonical URL so the two cannot drift
- [x] Transcript pages do the same — they also have a `.md` route
- [x] Pages with no twin carry no such link
- [x] Unit tests for the helper; build-integration assertion that every
      advertised href resolves to a file that actually exists in `dist/`,
      rather than to a plausible-looking path
- [x] Decide: full coverage or entry-only. If full:
  - [x] `.md.ts` routes for `/`, `/blog/`, `/projects/`, `/entries/`, `/tags/`
        and `/tags/<tag>`, generated from the collection
  - [x] `/about` and `/contact` prose moved to a single source that renders
        both the HTML and the twin
  - [x] Edge function rewrites every HTML path, with a build-integration
        assertion that **every** HTML route in `dist/` has a sibling `.md` —
        the invariant the blanket rewrite depends on
  - [x] A test that a path with no twin never rewrites to a 404
- [ ] Optional, decide separately: emit `x-markdown-tokens` on `.md` responses
- [ ] Optional: HTTP `Link` header — only if it can be scoped correctly, see
      below
- [x] Re-run `npm run crawlers`; the Markdown-negotiating profile must still
      pass

## Notes

**CloudFront constraint, checked 2026-09-15.** The distribution has no response
headers policy and **zero ordered cache behaviours** — everything is served by
the single default behaviour. A response headers policy applies to a whole
behaviour, so a global `Link:` header would assert a Markdown twin for every
page, including the ones that have none. Doing it correctly means adding an
ordered cache behaviour for `/entries/*` with its own policy. That is more
moving parts than the HTML link, for a narrower audience, and it is the same
blocker as the `x-markdown-tokens` header.

Recommend the HTML link element first. It is per-page by construction, so it
cannot make a false claim, and it needs no infrastructure change.

The edge function rewrites only paths under `/entries/` — see
`infra/live/function.js`. Extending negotiation to listings would mean
generating twins for them, which is a content decision rather than a routing
one.
